# K1Blog 通用软件工程规范

> 文档编号：03  
> 版本：v1.1.0  
> 上游：`00-项目执行宪法`、`01-入口文件与装配规范`、`02-企业级研发规范`  
> 适用范围：架构分层、服务端/客户端边界、前端组件、样式、动效、测试、部署、文档交付

## 0. 目的

把企业级通用软件工程规范落到 K1Blog 的 Next.js App Router + SQLite + Nginx 架构上。`02` 负责 API、错误码、数据库、代码风格、安全与发布；本文负责架构、分层、前端、测试、部署与文档。

## 1. 总则

### 1.1 核心原则

1. **单一职责**：入口只装配，页面只组合，服务只承载业务，组件只表达 UI。
2. **高内聚低耦合**：按 feature 聚合；模块间通过公开接口通信；禁止跨 feature 直接引用内部文件。
3. **开闭原则**：扩展通过新增 feature/组件/策略，不通过在原逻辑上堆条件分支。
4. **依赖倒置**：业务依赖抽象契约（schema、接口、仓储），不依赖具体实现细节。
5. **最小权限**：管理端、数据库、文件、环境变量、会话都按最小权限配置。
6. **可观测**：日志、错误、指标、请求 ID 覆盖关键路径；故障可追溯。
7. **环境隔离**：开发、预发、生产配置与数据分离；生产最小暴露。
8. **可复用可维护**：通用能力在 `lib/` 或 `components/ui`；不为一次性逻辑造抽象。

### 1.2 评判标准

可长期维护、可被他人安全接手、出事可追溯。不是「能跑通」、不是「看起来高级」、不是「代码行数少」。

## 2. 架构与分层

### 2.1 目录结构

```text
app/
  (site)/
    layout.tsx
    page.tsx
    posts/[slug]/page.tsx
    tags/[tag]/page.tsx
    archive/page.tsx
    search/page.tsx
    about/page.tsx
  (admin)/
    admin/
      layout.tsx
      login/page.tsx
      comments/page.tsx
  api/
    v1/
      health/live/route.ts
      health/ready/route.ts
      posts/[slug]/comments/route.ts
      admin/comments/route.ts
      admin/comments/[id]/route.ts
    auth/[...all]/route.ts
  error.tsx
  global-error.tsx
  not-found.tsx
  sitemap.ts
  robots.ts
  feed.xml/route.ts
  opengraph-image.tsx
components/
  ui/              # 设计系统原语与组合组件
  motion/          # 动效封装与 token 消费
  layout/          # 站点骨架、导航、页脚
  comments/        # 评论展示层（纯 UI）
features/
  content/         # MDX schema、加载、查询、MDX 渲染、搜索、SEO
  comments/        # 评论 schema、service、queries、actions、组件
  admin/           # 管理员守卫、审核流程
lib/
  db/              # SQLite 客户端、Drizzle schema、迁移、仓储
  auth/            # Better Auth 服务端封装
  env.ts           # Zod 环境变量单一入口
  errors/          # AppError、错误码、映射
  logging/         # 结构化日志
  rate-limit/      # 限流
  security/        # CSRF、哈希、加密、Origin 校验
  utils/           # 无业务依赖的纯工具
content/posts/     # MDX 内容
styles/            # tokens.css、base.css
scripts/           # entrypoint、内容校验、索引生成
tests/             # 跨模块测试与 fixtures
deploy/            # nginx.conf、compose、镜像相关
docs/              # 本规范体系
```

### 2.2 依赖方向

```text
app → features → lib
app → components → styles
features → components/ui, components/motion, lib
components → styles, lib/utils（仅纯工具）
lib → 无 app/features 依赖
```

铁律：

- `lib` 不得 import `app` 或 `features`。
- `components/ui` 不得 import `lib/db`、`lib/auth`、`features/**`。
- `features` 不得直接 import 另一个 feature 的内部文件；跨 feature 通过公开入口或提升到 `lib`。
- `app` 不得直接 import `lib/db`；只能通过 feature service/query。
- 禁止环形依赖；禁止 barrel 文件作为默认组织方式。
- 禁止跨层调用：页面不得直接写 SQL；组件不得直接写数据库；路由不得承载业务。

### 2.3 Feature 模块形状

每个 feature 必须自包含：

```text
features/comments/
  schema.ts        # Zod 入参/出参/领域类型
  service.ts       # 业务规则、事务、状态流转
  queries.ts       # 只读查询
  actions.ts       # Server Action 适配
  components/      # 该 feature 的 UI
  index.ts         # 唯一公开出口（只导出允许外部使用的内容）
```

规则：

- `schema.ts` 是契约来源；类型从 Zod 推导，不手写重复类型。
- `service.ts` 不依赖 React/DOM/Next 路由；可在 Node 测试中直接调用。
- `queries.ts` 只读、有界、明确字段；不写业务状态变更。
- `actions.ts` 只做校验、鉴权、调用 service、revalidate；不写业务。
- 内部文件不得被外部直接引用；只通过 `index.ts` 公开必要面。

### 2.4 服务端/客户端边界

- 默认 Server Component；只在需要浏览器交互、状态、动画控制时使用 `'use client'`。
- 客户端组件必须尽量小，放在叶子；不得把整页标记为 client。
- 禁止把数据库、认证、环境变量、日志、限流模块导入客户端。
- 服务端模块统一 `import 'server-only'`（`lib/db`、`lib/auth`、`lib/env`、`lib/logging`、`lib/rate-limit`、`features/comments/service`、`features/content/loader`）。
- 客户端不得读取 `process.env` 秘密；只允许 `NEXT_PUBLIC_` 公开值。
- 数据获取默认在 RSC 或 Route Handler；禁止在客户端重复拉取静态内容。
- 表单提交优先 Server Action；对外 API 走 `/api/v1`；两者都调用同一 service。

### 2.5 数据获取与状态

- 静态内容：构建期读取 MDX，生成页面；不在客户端请求文章 JSON。
- 动态数据：评论列表、审核队列通过 Route Handler 获取；页面内必要时用 Server Component 读取。
- 搜索：构建期索引 + 客户端检索；索引文件按版本缓存。
- 表单：`useOptimistic` 仅用于评论提交的即时反馈；失败必须回滚并显示错误。
- 全局状态：不引入 Zustand/Redux，除非出现跨页面、跨层、无法用 URL/RSC 表达的状态；引入前必须记录 ADR。
- URL 作为搜索/筛选状态来源；不得把可分享状态藏在组件内部。
- 禁止用 `useEffect` 做本可在服务端完成的数据读取。

### 2.6 错误边界与降级

- `app/error.tsx` 处理路由级错误；`global-error.tsx` 处理根级崩溃。
- 评论提交失败显示字段错误或统一错误区；不得白屏、不得静默。
- 数据不可用时显示明确的空状态/错误状态，不用假数据填空。
- 第三方服务失败（SMTP、人机验证）不得阻塞核心读路径；评论写入失败必须显式。

### 2.7 内容架构

- MDX 文件位于 `content/posts/`；frontmatter 由 `features/content/schema.ts` 校验。
- 加载器只允许服务端运行；构建期生成 slug、标签、归档、搜索索引、RSS、sitemap。
- MDX 只允许受控组件白名单；禁止任意 import、脚本、内联 HTML 执行。
- 代码高亮在构建期完成；客户端不加载高亮器。
- 草稿只在开发/预览可见；生产构建排除。
- 内容相关规则详见 `05`。

### 2.8 评论架构

- 评论是原生子系统，不使用第三方评论挂件。
- `features/comments` 负责 schema、service、queries、actions；`lib/db` 只提供数据库能力。
- 评论写入：校验 → 限流 → 幂等 → 反垃圾 → 事务写库 → 审计/通知。
- 评论读取：只返回已通过、未删除的评论；不返回 IP。
- 管理端：会话 + CSRF + 审计；审核状态机受约束。
- UI 完全使用项目设计系统，不使用第三方主题。
- 数据、审核、隐私规则详见 `05`。

### 2.9 管理端架构

- `/admin` 路由组独立布局；未登录跳转登录页。
- Better Auth 负责认证；`features/admin` 负责授权与审核流程。
- 管理端所有写操作必须 CSRF + 审计；读操作最小化返回字段。
- 管理端不得复用公开评论 DTO 中的敏感字段；使用独立 admin DTO。

## 3. 前端规范

### 3.1 组件

- Server Component 优先；Client Component 只用于交互、动画控制、浏览器 API。
- 组件 props 必须可序列化；不要把函数、类实例、数据库对象传给客户端。
- 组件只表达 UI；数据获取、业务规则、错误码映射放在 feature/service 或页面组合层。
- 组件文件 ≤ 200 行；超过拆分，不靠注释解释复杂度。
- 禁止为一次性布局造抽象；重复三次以上再抽。
- 组件必须有明确的可访问名称/角色；交互元素使用语义标签。
- 禁止默认导出（Next 约定文件除外）；使用命名导出，便于检索与重构。
- 禁止 `React.FC`；直接声明 props 类型。
- 禁止在渲染中做副作用；副作用放事件处理器或明确的客户端生命周期。

### 3.2 样式

- Tailwind CSS v4 + 设计 token；token 定义在 `styles/tokens.css`。
- 组件中禁止裸 hex、禁止随意 `rgb()`；使用语义 token（背景、文本、边框、强调、状态）。
- 禁止无依据的任意值（`w-[437px]`）；确需测量值时必须来自设计 token 或布局计算，并注明明原因。
- 禁止引入 UI 组件库默认主题；Radix 仅用于无障碍原语，外观完全自建。
- 禁止大面积阴影、发光、渐变、玻璃卡片堆叠、超大圆角、波纹、幕布升起、弹跳特效。
- 颜色只承担语义；全站强调色不超过一个主强调色，辅助色仅用于特定语义。
- 主题通过 `data-theme="night|lamp"`；禁止 FOUC；主题切换不得引发布局抖动。
- 样式层级使用 CSS layers；禁止 `!important` 作为常规手段。
- 禁止运行时 CSS-in-JS；禁止在客户端注入大段样式。
- 光标语义：可点击 `cursor: pointer`；禁用/处理中 `cursor: not-allowed`；仪器类交互可用 `crosshair`。
- 按钮在悬浮、按压、激活、聚焦状态均不得出现阴影；按压不得出现灰色波纹放大。
- 分页默认固定每页条数；当前页标记不得使用白色方块背景。
- 错误与危险状态使用红色文字直陈，不加底色方框、不加图标。
- 表单默认完全空白；禁止预填真实或示例敏感数据；禁止与功能无关的占位说明文案。
- 详细视觉规则见 `04`。

### 3.3 动效

- 只使用 `transform`、`opacity`、`clip-path` 等合成友好属性；禁止动画化宽高、top/left、margin 等触发布局的属性。
- 动效 token：120ms 微交互、240ms 标准、400ms 揭示、600ms 页面迁移；曲线统一 `cubic-bezier(0.2, 0.7, 0.1, 1)`。
- 禁止库默认弹簧；如确需惯性，必须是有测量依据的机械式阻尼。
- 禁止无限循环动画，唯一例外是首屏滚动提示，且必须在 `prefers-reduced-motion` 下停止。
- 禁止在滚动中做大量 parallax、逐帧计算、布局读取；滚动监听必须 passive + rAF 节流。
- `prefers-reduced-motion: reduce` 下所有动画即时完成，内容完整可见，不得留空。
- 动效服务于状态迁移与空间关系，不表演；一屏最多一个主动效焦点。
- 详细动效规范见 `04`。

### 3.4 图片与字体

- 图片统一 `next/image`，关闭运行时图片优化（`images.unoptimized`），以预生成的 AVIF/WebP 静态资源交付；必须提供 `alt`、宽高、尺寸策略。
- 单图 ≤ 200KB；大图使用响应式尺寸；禁止直接引用未优化原图。
- 图片风格遵循 `04`：双色/低饱和、技术图注、胶片颗粒；禁止 AI 插画与通用图库拼贴。
- 字体本地自托管；中文按 unicode-range 切片；首屏只加载必要子集；`font-display` 策略明确。
- 禁止引入整套中文字库；禁止首屏加载所有字重。
- 字体加载不得造成明显布局偏移；关键字体可 preload，但不超过 2 个文件。
- 禁止用图片替代真实文本标题/正文。

### 3.5 无障碍

- 目标 WCAG 2.2 AA。
- 正文对比度 ≥ 7:1；辅助文字 ≥ 4.5:1；大字与图形按标准。
- 所有交互可键盘操作；焦点可见，使用 2px 强调色描边，不得移除焦点样式。
- 图标按钮必须有 `aria-label`；装饰图 `aria-hidden`。
- 动态读数（时钟）不得使用会打扰读屏的 `aria-live`；需要时提供静态说明。
- 触控目标至少 44×44 CSS px；小文字链接需有足够点击区域。
- 主题切换、评论表单、审核操作必须可用键盘完成。
- 详细验收矩阵见 `04` 与 `06`。

### 3.6 SEO 与元数据

- 每页必须有唯一 `title`、`description`、canonical。
- 文章输出 `Article` JSON-LD；站点输出 `WebSite`/`Person` 结构化数据。
- sitemap、RSS、robots 必须与内容索引一致；草稿不得出现。
- OG 图使用本地字体子集与设计 token，不请求第三方服务。
- 禁止重复内容、软 404、无 canonical 的分页/标签页。
- 链接必须可抓取；不要用纯 JS 点击替代 `<a>`。

### 3.7 性能

- RSC 优先；静态页面 SSG；标签/归档按需 ISR；评论接口动态。
- 首屏 JS 目标 ≤ 160KB gzip，门禁 ≤ 180KB gzip。
- 首屏实际加载 ≤ 220KB；字体资产总包 ≤ 320KB；preload ≤ 2。
- 单页总重量目标 ≤ 1.2MB；图片按需加载。
- 禁止在首屏引入图表、编辑器、3D、重型动画库。
- 第三方脚本默认不允许；分析工具必须自托管或明确批准。
- 性能门禁与测量方法见 `06`。

## 4. 测试规范

### 4.1 测试分层

| 层 | 工具 | 范围 | 要求 |
| --- | --- | --- | --- |
| 单元 | Vitest | schema、纯工具、错误映射、限流、加密、内容解析 | 快速、确定性、无网络 |
| 集成 | Vitest + 临时 SQLite | service、route handler、迁移、评论状态机 | 每个用例独立库；跑完清理 |
| 端到端 | Playwright | 首页、文章、搜索、评论提交、管理员审核、主题切换 | 真实浏览器；固定种子 |
| 视觉 | Playwright 截图 | 390/768/1440/1920；深色/浅色；减弱动效 | 与设计基线对比 |
| 无障碍 | axe + 手动 | 键盘、焦点、对比度、语义、减弱动效 | 无 critical/serious |
| 性能 | Lighthouse CI | 首页/文章页 | 按 `06` 预算 |
| 安全 | 单元/集成/扫描 | XSS、SQLi、CSRF、限流、幂等、鉴权、依赖 | 失败路径必须覆盖 |
| 内容 | 脚本 + 构建 | frontmatter、slug、链接、图片、草稿 | 构建失败即阻断 |

### 4.2 测试质量

- 测试必须能在实现出错时失败；恒过的测试视为无效。
- 断言行为与边界，不断言内部实现细节。
- 覆盖成功、失败、边界、并发/重复提交（如适用）。
- 禁止 mock 掉被测对象本身；只 mock 外部依赖。
- 测试数据必须是合成数据，不得使用生产数据或真实个人信息。
- 时间、随机、UUID、网络必须可控；否则测试不可重复。
- 快照测试只用于稳定结构/视觉基线，不得用快照替代行为断言。
- 覆盖率不是唯一指标：核心领域（评论、内容 schema、权限、加密、限流）分支覆盖 ≥ 90%；整体 ≥ 80%；UI 视觉由截图门禁覆盖。

### 4.3 必测路径

- 首页/文章/标签/归档/搜索在无数据、正常、异常情况下不白屏。
- 评论：空字段、超长、非法父评论、重复幂等键、限流、垃圾内容、审核通过后可见、删除后不可见。
- 管理端：未登录、会话过期、CSRF 缺失、越权、状态冲突、审核审计。
- 数据：空库迁移、既有库迁移、备份恢复、外键约束。
- 主题：深色/浅色切换、刷新后保持、无 FOUC、减弱动效。
- 响应式：无横向溢出；移动端触控目标；导航可达。

## 5. 部署与运维

### 5.1 镜像

- 多阶段构建：依赖 → 构建 → 运行；生产镜像不包含源码、测试、开发依赖。
- 基础镜像 Node 22 LTS；SQLite 原生模块使用兼容的 Debian slim 基础镜像。
- 非 root 用户运行；只读根文件系统（SQLite 数据卷与 `/tmp` 可写）。
- 设置 `NEXT_TELEMETRY_DISABLED=1`、`HOSTNAME=0.0.0.0`、`PORT=3000`。
- 健康检查命中 `/api/v1/health/live`；就绪检查命中 `/api/v1/health/ready`。
- 镜像 Tag 与版本号一致；禁止 `latest` 上线。

### 5.2 Nginx

- TLS 1.2/1.3、HTTP/2、HSTS；关闭 `server_tokens`。
- 安全响应头与 CSP；静态资源 immutable 缓存；HTML 不长缓存。
- 评论写接口与登录接口单独限流；请求体限制；超时设置。
- 反向代理到 Next standalone；保留 `X-Request-Id`；不缓存 API。
- 部署前 `nginx -t`；配置变更必须评审与回滚。

### 5.3 数据库与迁移

- 单实例 SQLite；WAL；数据卷独立挂载；备份到异机/对象存储。
- 部署前备份；迁移由 entrypoint 显式执行；迁移失败即停止发布。
- 迁移采用 expand/contract；破坏性变更必须单独审批。
- 恢复演练按 `05` 执行。

### 5.4 发布、回滚与监控

- 发布顺序：备份 → 构建 → 停止旧实例 → 迁移 → 启动新实例 → 健康检查 → Nginx 切换 → 冒烟。
- 回滚：切换上一镜像 Tag；若迁移不可逆，恢复备份；记录原因与影响。
- 监控：5xx 比例、P95、评论写入失败、数据库大小、磁盘、备份状态。
- 日志：结构化、脱敏、滚动保留；Nginx 与应用日志分离。
- 事故处理：先止损，再根因；保留证据；事后复盘，不追责式叙述。

## 7. 评审与重构

### 7.1 Code Review 必查

1. 是否出现魔法值、硬编码配置、硬编码文案与版本号。
2. 是否跨层调用、在入口/页面写业务、在组件写数据访问。
3. 是否在日志/错误/响应中泄露邮箱、IP、令牌、堆栈、路径。
4. 输入是否全部校验；失败路径是否覆盖。
5. 是否吞异常、默认值掩盖失败、用 TODO 掩盖未完成。
6. 是否引入不必要的依赖、默认 UI 主题、与设计系统冲突的样式。
7. 是否触碰 `04` 的反模板红线、无障碍要求、动效预算。
8. 是否有备份/回滚路径；是否覆盖数据迁移风险。
9. 是否更新文档、测试、契约。
10. 是否夹带无关变更。

### 7.2 强制重构阈值

满足任一条必须重构：

- 单函数 > 80 行；嵌套 > 3 层；参数 > 3 且无对象封装。
- 组件 > 200 行；feature service > 300 行；入口 > 规定上限。
- 同一逻辑重复 ≥ 3 次；跨 feature 复制粘贴。
- 文件目录平铺、职责混杂，新增功能需要跨多个无关目录改动。
- 核心逻辑无测试；测试只能靠快照；关键失败路径未覆盖。
- 性能门禁连续失败且原因无法定位。
- 设计实现开始用补丁覆盖补丁，token 失效。

不得以「先上线再重构」越过安全、数据、无障碍与设计底线。

## 8. ADR（架构决策记录）

出现以下变更必须写 ADR，存于 `docs/adr/`：

- 引入/替换核心框架、数据库、认证、评论引擎、部署拓扑。
- 改变公共 API 契约、错误码体系、数据模型。
- 改变设计 token 语义、主题策略、字体/动效体系。
- 引入全局状态库、重型客户端依赖、WebGL/3D。
- 改变备份/恢复、隐私、安全策略。

模板：

```text
# ADR-{编号}: {标题}
状态：提议 / 已接受 / 已废弃
背景：
决策：
备选方案：
后果（正面 / 负面）：
验证方式：
```

ADR 与代码同 PR；未接受的 ADR 不得作为既成事实实现。

## 9. 落地执行口诀

1. 入口只装配，业务全下沉。
2. 分层单向，服务端先行。
3. schema 先行，输入必校验。
4. 密钥不落地，日志必脱敏。
5. 设计走 token，动效有预算。
6. 测试可失败，证据可复现。
7. 备份再迁移，回滚先想好。
8. 文档同变更，合并过门禁。
