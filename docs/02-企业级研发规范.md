# K1Blog 企业级研发规范

> 文档编号：02  
> 版本：v1.1.0  
> 上游：`00-项目执行宪法`、`01-入口文件与装配规范`  
> 适用范围：API、错误码、数据库、代码风格、分支与发布、配置、异常与返回值、安全、可观测性、依赖治理

## 0. 与通用企业模板的偏差声明

本规范以企业级通用模板为骨架，但按 K1Blog 的实际技术栈做了以下明确偏离。偏离不是降标，而是为了更可验证、更贴合单实例自托管博客：

| 事项 | 通用模板 | 本项目 | 原因 |
| --- | --- | --- | --- |
| API 成功响应 | `{ code: 0, message, data }` | HTTP 2xx + `{ data, meta? }` | 保持 HTTP 语义，避免业务码与 HTTP 状态双重表达 |
| API 错误响应 | `{ code, message, trace_id }` | RFC 9457 `application/problem+json` + 稳定 `code` | 标准错误结构，便于客户端与日志统一处理 |
| 主键 | bigint / 雪花 | UUIDv7（TEXT） | 单实例 SQLite 下可移植、可按时间排序、不暴露自增规模 |
| 时间字段 | `create_time` / `update_time` | `created_at` / `updated_at` / `deleted_at` | 与 SQL/Drizzle 生态一致，软删除保留时间语义 |
| 外键 | 禁止 | 仅对 `comment.parent_id` 启用自引用外键 | SQLite 单写者场景下保障评论树完整性 |
| 代码缩进 | Java 4 空格 | TS/TSX 2 空格 | 与前端生态、Prettier 默认一致 |
| 分支模型 | GitFlow 或 TBD | Trunk Based Development | 单人维护、短生命周期分支、持续集成 |
| 分层 | Controller/Service/Mapper | Route Handler / feature service / repository | Next.js App Router 的服务端分层 |

# 1. API 设计规范

## 1.1 范围与入口

- 对外 API 统一前缀 `/api/v1`，JSON，UTF-8。
- 内容页、搜索索引走静态生成，不提供文章 CRUD API。
- 认证路由由 Better Auth 挂载在 `/api/auth/*`，是 `/api/v1` 的唯一例外；不得在 `/api/v1` 下重复实现登录。
- 管理端接口统一在 `/api/v1/admin/*`，必须经过会话校验、CSRF 校验与审计。

## 1.2 端点基线

| 方法 | 路径 | 用途 | 认证 | 限流 |
| --- | --- | --- | --- | --- |
| GET | `/api/v1/health/live` | 进程存活 | 无 | 无 |
| GET | `/api/v1/health/ready` | 数据库可读 | 无 | 无 |
| GET | `/api/v1/posts/{slug}/comments` | 获取已通过的评论 | 无 | 60/min/IP |
| POST | `/api/v1/posts/{slug}/comments` | 提交留言，自动判定或进入待审 | 无 | 5/min/IP、20/h/IP |
| GET | `/api/v1/admin/comments` | 留言台账，分页 | 管理员会话 | 60/min/会话 |
| PATCH | `/api/v1/admin/comments/{id}` | 人工通过/拒绝/标记垃圾 | 管理员会话 + CSRF | 30/min/会话 |
| DELETE | `/api/v1/admin/comments/{id}` | 软删除评论 | 管理员会话 + CSRF | 30/min/会话 |
| GET | `/api/v1/admin/moderation/policy` | 读取自动审核策略 | 管理员会话 | 60/min/会话 |
| PUT | `/api/v1/admin/moderation/policy` | 保存策略并复核存量待审 | 管理员会话 + CSRF | 30/min/会话 |

新增端点必须先改本文与 OpenAPI 契约，再写实现。

## 1.3 URL 与方法

- 使用名词复数，路径全小写，单词用连字符；禁止 `/getComment` 一类动词路径。
- 资源层级通过路径表达：`/posts/{slug}/comments`。
- `GET` 只读、无副作用；`POST` 创建；`PATCH` 部分更新；`DELETE` 删除。
- 路径参数必须校验格式；`slug` 只允许小写 ASCII 字母、数字、连字符。
- 不在 URL 中放邮箱、IP、令牌、内部 ID 以外的敏感信息。

## 1.4 请求与响应

### 成功

- `2xx` + JSON body。
- 单资源：`{ "data": { ... } }`。
- 列表：`{ "data": { "items": [...], "nextCursor": "..." }, "meta": { ... } }`。
- 创建评论：`202 Accepted`，`{ "data": { "id": "...", "status": "approved" | "pending" } }`；不返回正文，也不公开拦截分类。
- 自动审核策略：GET 返回当前修订快照；PUT 校验完整策略、追加修订，并在同一事务内复核存量待审，返回复核计数。
- 无内容：`204 No Content`，不返回 body。

### 错误

- 使用 `Content-Type: application/problem+json`，HTTP 状态码作为主要信号。
- 结构：

```json
{
  "type": "urn:k1blog:error:comment-invalid",
  "title": "评论无法提交",
  "status": 422,
  "detail": "评论内容超出长度限制",
  "instance": "/api/v1/posts/example/comments",
  "code": "K1-CMT-003",
  "traceId": "req-...",
  "errors": [
    { "field": "content", "message": "最多 2000 字" }
  ]
}
```

- `detail` 面向用户，不含堆栈、SQL、路径、内部类名。
- `errors` 仅在字段级校验失败时出现。
- 错误响应必须带 `X-Request-Id`，并在服务端日志记录完整上下文。
- 禁止返回 `err.stack`、数据库错误原文、内部文件路径。

## 1.5 HTTP 状态码

| 状态 | 场景 |
| --- | --- |
| 200 | 查询成功、审核成功 |
| 201 | 需要即时创建并返回资源的场景（本项目评论为 202，不使用 201） |
| 202 | 评论已接收，进入待审 |
| 204 | 删除成功，无 body |
| 400 | 请求体不是合法 JSON、路径参数格式错误 |
| 401 | 管理员未登录/会话失效 |
| 403 | 无权限、CSRF 失败、Origin 不允许 |
| 404 | 文章或评论不存在 |
| 409 | 状态冲突（重复审核、并发审核被他人抢先） |
| 422 | 字段校验失败、评论过长、父评论层级非法 |
| 429 | 触发限流 |
| 500 | 未分类服务端错误 |
| 503 | 数据库不可用、依赖未就绪 |

## 1.6 分页、过滤、排序

- 公共评论列表使用游标分页：`cursor` 为不透明字符串，`limit` 默认 20，最大 50。
- 管理端队列使用页码分页：`page` 从 1 开始，`pageSize` 默认 20，最大 50；响应 `meta` 含 `page`、`pageSize`、`total`。
- 公共接口不接受任意排序字段；固定按 `created_at ASC, id ASC`（评论阅读顺序）。
- 管理端只允许 `status`、`page`、`pageSize` 三个过滤/分页参数。
- 禁止把用户输入直接拼进 SQL、排序字段、列名。

## 1.7 幂等与并发

- `POST /api/v1/posts/{slug}/comments` 必须带 `Idempotency-Key`，长度 16–64，字符集受限。
- 服务端存储 `HMAC-SHA256(Idempotency-Key, COMMENT_IP_PEPPER)`，唯一索引；24 小时内重复请求返回第一次的结果，不重复写库。
- 审核状态流转必须在一个事务内完成，并同时写审计日志。
- 同一评论的并发审核使用状态条件更新；更新结果为 0 行时返回 `409`，不覆盖他人操作。
- 评论父节点必须存在、已通过、未删除，层级最多 2（顶层 + 一级回复）。

## 1.8 认证、授权与 CSRF

- 管理员认证使用 Better Auth，会话 Cookie：`HttpOnly`、`Secure`（生产）、`SameSite=Lax`。
- 管理端写请求必须校验 CSRF：双提交 Cookie 或同源 Token；缺少或不匹配返回 `403 K1-AUTH-003`。
- 评论提交为匿名，不要求登录；但必须校验 Origin/Referer 同源，跨站请求拒绝。
- 管理端接口同时校验会话与角色；权限最小化，不做“登录即可全部操作”。
- 会话过期、登出、密码修改后旧会话失效；敏感操作写入审计日志。

## 1.9 CORS、缓存与请求追踪

- 默认同源；不开启 `Access-Control-Allow-Origin: *`。
- 如未来有外部只读 API，允许列表必须来自环境变量，逐域校验，且不带凭据。
- 评论 API：`Cache-Control: no-store`。
- 健康检查：`no-store`。
- 静态内容：由 Next/Nginx 使用 immutable 缓存；API 不复用静态缓存。
- 所有响应带 `X-Request-Id`；Nginx 生成，应用透传；日志与错误响应一致。

## 1.10 版本与废弃

- 新版本使用 `/api/v2`，不得原地破坏 `/api/v1`。
- 废弃接口至少保留一个过渡期，响应头增加 `Deprecation` 与 `Sunset`。
- 删除接口前必须确认无调用方、更新 OpenAPI、更新本文档。
- 契约变更（字段、状态码、错误码）必须在 PR 中标注，并同步客户端。

# 2. 错误码规范

## 2.1 编码结构

统一格式：`K1-{模块}-{三位编号}`。

- `K1`：项目固定前缀。
- 模块：`SYS`、`REQ`、`AUTH`、`CMT`、`DB`、`SEC`、`ADM`。
- 编号：三位数字，模块内递增。

错误码是稳定契约，不得复用、不得改变语义、不得删除后重新分配。

## 2.2 注册与使用

- 所有错误码集中定义在 `lib/errors/codes.ts`，包含：
  - `code`；
  - HTTP 状态；
  - 中文用户消息；
  - 日志级别；
  - 是否可重试；
  - 字段级错误模板（可选）。
- 服务层抛出 `AppError`，只携带错误码与安全上下文；Route Handler 统一映射为 problem+json。
- 客户端只能依据 `code` 做逻辑分支，禁止依据 `message` 文本。
- CI 扫描魔法错误码字符串；未注册的 `K1-*` 直接失败。

## 2.3 基线错误码

| 错误码 | HTTP | 含义 | 级别 |
| --- | --- | --- | --- |
| `K1-SYS-000` | 500 | 未分类内部错误 | error |
| `K1-REQ-001` | 400 | 请求体非法 JSON | warn |
| `K1-REQ-002` | 400 | 路径/查询参数格式错误 | warn |
| `K1-AUTH-001` | 401 | 未登录或会话失效 | warn |
| `K1-AUTH-002` | 403 | 权限不足 | warn |
| `K1-AUTH-003` | 403 | CSRF 校验失败 | warn |
| `K1-AUTH-004` | 429 | 登录尝试过多 | warn |
| `K1-CMT-001` | 404 | 文章不存在 | info |
| `K1-CMT-002` | 404 | 评论不存在 | info |
| `K1-CMT-003` | 422 | 评论字段非法/超长 | info |
| `K1-CMT-004` | 422 | 父评论不存在/层级非法 | info |
| `K1-CMT-005` | 422 | 评论被安全策略硬拒绝 | info |
| `K1-CMT-006` | 409 | 评论状态冲突 | warn |
| `K1-CMT-007` | 429 | 评论提交过于频繁 | warn |
| `K1-DB-001` | 503 | 数据库不可用 | error |
| `K1-DB-002` | 500 | 数据写入失败 | error |
| `K1-SEC-001` | 403 | 请求来源不允许 | warn |
| `K1-ADM-001` | 409 | 审核状态已被他人变更 | warn |

新增错误码必须先更新本表与常量文件；禁止在代码中直接写字符串。

# 3. 数据库设计规范

## 3.1 数据库与运行约束

- SQLite，WAL 模式，单写者；单实例部署。
- 启动时设置：`journal_mode=WAL`、`busy_timeout=5000`、`foreign_keys=ON`。
- 所有写操作通过 feature service，不在 Route Handler/页面/组件中直接写库。
- 禁止在 `proxy`/`middleware`、Edge runtime、客户端代码中访问数据库。
- 事务只包裹必要的写操作；不得在事务内发起网络请求、发邮件、写日志文件。
- 查询必须有界：分页、`LIMIT`、明确的过滤条件；禁止无界列表。

## 3.2 命名与基础字段

- 表名：小写、单数、下划线，如 `comment`、`moderation_audit`。
- 字段名：小写、下划线，如 `post_slug`、`created_at`。
- 索引：`idx_表_字段`，唯一索引 `uk_表_字段`。
- 主键：`id`，TEXT，UUIDv7；禁止暴露自增 ID。
- 每张业务表必须包含：`id`、`created_at`、`updated_at`；软删除表加 `deleted_at`。
- 时间存 UTC 毫秒整数；API 输出 ISO 8601 UTC 字符串。
- 禁止使用保留字、拼音与英文混用、无意义缩写。

## 3.3 评论数据模型

### `comment`

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | TEXT | PK | UUIDv7 |
| `post_slug` | TEXT | NOT NULL | 文章 slug，来自内容索引 |
| `parent_id` | TEXT | NULL，FK `comment.id` `ON DELETE SET NULL` | 顶层为空；最多两级 |
| `author_name` | TEXT | NOT NULL，1–40 字符 | 展示名 |
| `content` | TEXT | NOT NULL，1–2000 字符 | 纯文本，不存 HTML |
| `status` | TEXT | NOT NULL，CHECK `pending/approved/rejected/spam` | 审核状态 |
| `ip_hash` | TEXT | NOT NULL | 带 pepper 的哈希 |
| `user_agent_summary` | TEXT | NULL，≤120 字符 | 截断摘要，不存完整 UA |
| `idempotency_key_hash` | TEXT | NOT NULL，UNIQUE | 24h 幂等键哈希 |
| `created_at` | INTEGER | NOT NULL | UTC 毫秒 |
| `updated_at` | INTEGER | NOT NULL | UTC 毫秒 |
| `moderated_at` | INTEGER | NULL | 审核时间 |
| `moderated_by` | TEXT | NULL | 管理员 ID |
| `moderation_note` | TEXT | NULL，≤500 字符 | 审核备注 |
| `deleted_at` | INTEGER | NULL | 软删除时间 |

### `moderation_audit`

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `id` | TEXT | PK，UUIDv7 |
| `actor_id` | TEXT | NOT NULL；管理员 ID 或 `system` |
| `action` | TEXT | NOT NULL，`approve/reject/spam/delete/restore` |
| `comment_id` | TEXT | NOT NULL |
| `from_status` | TEXT | NULL |
| `to_status` | TEXT | NULL |
| `note` | TEXT | NULL，≤500 |
| `created_at` | INTEGER | NOT NULL |

### 索引

- `uk_comment_idempotency (idempotency_key_hash)`
- `idx_comment_post_status_created (post_slug, status, created_at)`
- `idx_comment_parent_status (parent_id, status)`
- `idx_comment_status_created (status, created_at)`
- `idx_audit_comment_created (comment_id, created_at)`

### 关联与完整性

- 启用 `PRAGMA foreign_keys=ON`。
- 仅为 `comment.parent_id` 建立自引用外键，`ON DELETE SET NULL`，避免硬删除父评论时丢失回复。
- 有回复的父评论不得自动硬删除；仅在无回复时按保留策略清理，确保不产生可见的孤立回复。
- `post_slug` 不对 Git 内容建外键；写入前必须通过内容索引校验文章存在且已发布。
- 删除采用软删除；硬删除只由保留策略任务执行，并写审计。

## 3.4 迁移

- 使用 `drizzle-kit generate` 生成迁移，存于 `drizzle/`，纳入版本控制。
- 已应用迁移禁止修改；变更通过新迁移实现。
- 迁移前必须备份；破坏性迁移（删列、改类型、重写表）必须单独确认。
- 迁移必须在空库与既有库上分别验证；迁移后执行 `/api/v1/health/ready`。
- 回滚策略：优先应用反向迁移；无法反向时使用迁移前备份恢复。
- 禁止在应用启动时自动执行未经审核的迁移；迁移由 `scripts/entrypoint.mjs` 显式调用。

## 3.5 查询与性能

- 禁止 `SELECT *`；Drizzle 查询明确列出字段。
- 禁止循环内查询（N+1）；批量读取、批量写入。
- 所有列表查询必须有 `LIMIT` 或游标边界。
- 高频查询必须有索引；新增查询前用 `EXPLAIN QUERY PLAN` 验证。
- 索引列上禁止函数/表达式；联合索引遵循最左前缀。
- 单表索引数量控制在 5–6 个以内，新增前评估写放大。
- 大文本只存评论正文与审核备注；不把富文本、文件、图片二进制塞进 SQLite。

## 3.6 数据生命周期

| 数据 | 保留策略 |
| --- | --- |
| 已通过评论 | 长期保留，直到作者删除或用户请求删除 |
| 待审评论 | 30 天未处理则清理 |
| 拒绝/垃圾评论 | 30 天后硬删除 |
| 软删除评论 | 无回复的软删除评论 30 天后硬删除；有回复的父评论保留墓碑，不自动硬删除 |
| 审核审计 | 180 天 |
| 备份 | 30 天，日备；每月恢复演练 |

删除留言、IP 哈希等个人数据必须通过明确请求与审计流程；不得在日志中保留副本。

## 3.7 备份与恢复

- 每日执行 SQLite 在线备份（`.backup` 或 `VACUUM INTO`），生成独立文件并校验完整性。
- 备份文件不得与数据库同盘；至少保留一份异机/对象存储副本。
- 每次迁移前额外备份；备份失败则中止迁移。
- 每月至少一次恢复演练：恢复至临时目录、执行完整性检查、抽查评论与审计数据。
- 备份与恢复操作必须记录操作者、时间、文件校验值与结果；不记录数据库内容。

# 4. 代码风格与命名规范

## 4.1 格式

- TypeScript/TSX：2 空格缩进，禁止 Tab；单行 ≤ 100 字符；UTF-8；LF；文件末尾一个空行。
- 仓库根目录 `.editorconfig` 固化缩进、UTF-8、LF、末尾空行；`.gitattributes` 统一 `* text=auto eol=lf`，字体/图片标记 binary。
- 使用 Prettier 统一格式化；ESLint 9 flat config；提交前与 CI 必须通过。
- 字符串默认单引号；JSX 属性使用双引号；尾随逗号按 Prettier 配置。
- 禁止提交未格式化的代码；禁止用格式化制造无关 diff。

## 4.2 TypeScript

- `strict: true`，开启 `noUncheckedIndexedAccess`、`exactOptionalPropertyTypes`（如与框架兼容）。
- 禁止 `any`；未知输入用 `unknown` + Zod/类型守卫收窄。
- 禁止非空断言 `!` 除非已有前置校验且能说明依据；优先显式判空。
- 禁止 `@ts-ignore`；确需抑制时用 `@ts-expect-error` 并写明原因，且不得长期保留。
- 类型别名用 `type`；可扩展对象契约用 `interface`；禁止 `I` 前缀。
- 禁止 `enum`；用 `as const` 对象 + 联合类型，便于序列化与穷尽检查。
- 公共函数必须有显式返回类型；内部短函数可推断。
- 使用 `satisfies` 校验配置对象形状，不用强制断言。

## 4.3 命名

- 文件：kebab-case；React 组件文件 PascalCase；测试 `*.test.ts(x)`。
- 变量/函数：camelCase；类型/组件：PascalCase；常量：UPPER_SNAKE_CASE。
- 布尔：`is` / `has` / `can` / `should` 开头。
- 事件处理器：`handleX`；异步函数名表达动作，不表达实现。
- 数据库字段：snake_case；环境变量：UPPER_SNAKE_CASE；CSS token：`--kebab-case`。
- 禁止无意义缩写（`tmp`、`data2`、`obj`）；禁止拼音与英文混用。

## 4.4 结构与复杂度

| 项 | 阈值 |
| --- | --- |
| Route Handler | ≤ 120 行 |
| Server Action | ≤ 120 行 |
| React 组件 | ≤ 200 行 |
| feature service | ≤ 300 行 |
| hook | ≤ 150 行 |
| 单函数 | 建议 ≤ 50 行，硬上限 80 行 |
| 嵌套层级 | ≤ 3 层 |
| 参数数量 | ≤ 3；更多用对象 |
| 圈复杂度 | ≤ 10 |

超过阈值必须拆分；不得用注释解释“这里很复杂”而保留。

## 4.5 导入与依赖方向

- 使用 `@/` 绝对路径；禁止深层相对路径超过两级。
- 导入分组：标准库 → 第三方 → 内部绝对路径 → 相对路径 → 类型 → 样式。
- 使用 `import type`；禁止运行时导入仅用于类型。
- 禁止环形依赖；禁止 barrel 文件（`index.ts` 统一 re-export）作为默认组织方式。
- 依赖方向：`app` → `features` → `lib`；`components/ui` 不依赖业务；`lib` 不依赖 `app/features`。
- 跨 feature 只能通过该 feature 的公开入口；不得直接引用内部文件。

## 4.6 注释

- 注释只解释「为什么」，不解释「做什么」；代码本身应表达做什么。
- 禁止在注释中放外部文档链接、编号、工单号、聊天记录、临时结论。
- 注释必须自包含、可验证、无冲突；过时注释视为缺陷。
- 禁止注释掉的死代码；删除而不是保留。
- TODO 只允许在确有后续动作时使用，格式 `TODO(owner): 原因`；不得用 TODO 掩盖未完成功能。
- 公共 API 的 JSDoc 只写调用者必须知道的契约、副作用与失败条件，不复述类型。

## 4.7 错误处理

- 领域错误统一抛 `AppError`，携带稳定错误码与安全上下文；禁止抛字符串/普通对象。
- 禁止空 `catch`；禁止 `catch` 后默认值吞错；禁止把异常当正常控制流。
- 只在边界层记录一次错误日志；避免每层重复打印。
- 对外错误映射只暴露错误码、用户消息、请求 ID；内部细节写日志。
- 异步代码必须处理 rejection；禁止 floating promise。

## 4.8 配置

- 所有环境变量通过 `lib/env.ts` 的 Zod schema 读取；禁止散落 `process.env`。
- `.env.example` 只列键名、用途、是否必需、示例占位；不得放真实值。
- `NEXT_PUBLIC_` 只允许公开配置；密钥、邮箱、IP、令牌禁止。
- 配置命名：`APP_ENV`、`SITE_URL`、`DATABASE_PATH`、`BETTER_AUTH_SECRET`、`COMMENT_IP_PEPPER`、`SMTP_URL`。
- 生产环境缺少必需配置直接启动失败；不得回退到默认密钥。

## 4.9 版本与构建脚本

- 版本号唯一来源：`package.json`；其他位置只读取，不重复维护。
- 构建/启动脚本只使用 ASCII 输出，避免 Windows 终端编码问题。
- 禁止把版本号硬编码到页面、脚本、Dockerfile；需要展示时从统一常量读取。
- 依赖版本锁定；禁止 `latest`、`*`、快照版。

# 5. 分支、提交与发布

## 5.1 分支模型

采用 Trunk Based Development：

- `main` 为唯一长期分支，受保护，禁止直接推送。
- 功能分支：`feat/{short-desc}`；修复：`fix/{short-desc}`；文档：`docs/{short-desc}`；紧急修复：`hotfix/{short-desc}`。
- 分支生命周期尽量短；合并后删除。
- 不设长期 `develop`；集成分支即 `main`，靠 CI 保证主干可发布。

## 5.2 提交规范

使用 Conventional Commits：

```text
<type>(<scope>): <subject>
```

类型：`feat`、`fix`、`refactor`、`perf`、`docs`、`test`、`build`、`chore`、`security`。

要求：

- 一个提交只做一件事；禁止把格式化、重构、功能混在一起。
- 提交信息说明「为什么」，不逐行复述 diff。
- 禁止提交密钥、`.env`、数据库文件、备份、日志、临时截图。
- 提交前核对暂存范围；禁止 `git add -A` 带入无关文件。

## 5.3 合并与评审

- 所有变更通过 Pull Request；单人维护也不例外。
- PR 必须包含：目标、改动面、验证证据、风险、回滚方式、适用文档编号。
- CI 必须通过：Lint、类型检查、单元/集成测试、构建、内容校验、安全扫描、UI 视觉门禁（如适用）。
- 至少完成一次自查清单；有条件时由第二人复核。
- 合并策略使用 Squash Merge，保持主干历史可读。
- 禁止绕过 CI、删除测试、降低断言、跳过安全检查。

## 5.4 发布

- 语义化版本 `MAJOR.MINOR.PATCH`；版本唯一来源 `package.json`。
- 发布前：备份数据库、验证 Nginx 配置、构建镜像、跑冒烟测试。
- 发布顺序：备份 → 停止旧实例 → 迁移 → 启动新实例 → 健康检查 → Nginx 切换 → 冒烟。
- 发布后监控错误率、P95 延迟、评论写入失败率、数据库大小。
- 回滚：回退镜像 Tag；如迁移不可逆，恢复迁移前备份。回滚后必须记录原因与影响。

# 6. 安全开发规范

## 6.1 认证与授权

- 管理员认证使用 Better Auth；密码哈希由标准实现处理，禁止自创算法。
- 管理员初始化使用一次性本地 CLI；bootstrap 凭据不进入生产环境变量、仓库、日志；完成后删除。
- 会话 Cookie：`HttpOnly`、`Secure`、`SameSite=Lax`；生产环境必须 HTTPS。
- 登录失败限制：5 次/分钟/IP、15 次/小时/IP；超限返回 429，不泄露账号是否存在。
- 管理端权限最小化；所有写操作审计。
- 评论者匿名；不采集密码、不要求登录。

## 6.2 输入与输出

- 所有外部输入（路径、查询、Body、Header、Cookie）必须 Zod 校验。
- 评论正文按纯文本存储与输出；禁止 `dangerouslySetInnerHTML`、禁止 Markdown 转 HTML 后直接渲染。
- 评论中的 URL 不自动生成可点击链接；如需链接，必须显式、白名单、`rel="nofollow ugc noopener"`。
- MDX 只允许受控作者编写；禁止用户提交 MDX。
- 错误响应不包含内部路径、SQL、堆栈、密钥。
- 日志脱敏：邮箱、IP、令牌、Cookie、Authorization 不落明文。

## 6.3 注入与浏览器安全

- SQL 使用参数化查询/Drizzle，禁止字符串拼接；禁止把用户输入作为列名/排序字段。
- XSS：评论纯文本转义；MDX 禁止任意 HTML 注入；CSP 限制脚本来源。
- CSRF：管理端写操作使用双提交 Token + SameSite；跨站请求拒绝。
- 点击劫持：`frame-ancestors 'none'` / `X-Frame-Options: DENY`。
- MIME 嗅探：`X-Content-Type-Options: nosniff`。
- 开放重定向：只允许站内相对路径或白名单域名。
- SSRF：OG 图/内容抓取不得请求任意用户 URL；如必须，使用域名白名单、超时、响应大小限制。
- 路径遍历：文件读取只允许 `content/` 与受控资源目录；禁止用户控制路径。

## 6.4 依赖与供应链

- 新增依赖必须评审：必要性、许可证、维护状态、体积、安全记录。
- 禁止快照版、废弃包、来源不明包；锁定版本与 integrity。
- CI 运行 `pnpm audit --prod`；高危漏洞阻断发布。
- 定期升级安全补丁；升级必须跑完整门禁。
- 禁止从不受信源复制代码片段进入生产。

## 6.5 隐私

- 留言不收集邮箱；IP 只存哈希；User-Agent 截断摘要。
- 不采集与业务无关的个人信息；不接入第三方跟踪脚本。
- 提供隐私说明、删除请求渠道；删除必须审计。
- 备份同样视为包含个人信息，必须加密与限权访问。

## 6.6 安全响应头与 CSP 基线

Nginx 与 Next 响应头必须一致；冲突时取更严格者，并以实际 `curl -I` 结果为准。

| 响应头 | 基线值 |
| --- | --- |
| `Strict-Transport-Security` | `max-age=63072000; includeSubDomains`（预发布验证后再考虑 preload） |
| `X-Content-Type-Options` | `nosniff` |
| `X-Frame-Options` | `DENY` |
| `Referrer-Policy` | `strict-origin-when-cross-origin` |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=(), payment=()` |
| `Cross-Origin-Opener-Policy` | `same-origin` |
| `Cross-Origin-Resource-Policy` | `same-origin` |

CSP 基线：

```text
default-src 'self';
script-src 'self' 'nonce-{request}' 'strict-dynamic';
style-src 'self' 'unsafe-inline';
img-src 'self' data: blob:;
font-src 'self';
connect-src 'self';
frame-ancestors 'none';
base-uri 'self';
form-action 'self';
object-src 'none';
upgrade-insecure-requests;
```

规则：

- 优先 nonce/hash；Next.js 的脚本注入方式以锁定版本支持为准。
- 禁止 `unsafe-eval`；`style-src` 如必须保留 `'unsafe-inline'`，必须记录原因并在下一版本评估移除。
- 不接入第三方脚本；如确需，必须单独域名白名单、`report-to` 与安全评审。
- Cookie 使用 `HttpOnly`、`Secure`（生产）、`SameSite=Lax`、`Path=/`；认证 Cookie 优先 `__Host-` 前缀。
- CSP 变更必须用浏览器实测，不得只在 Nginx 配置里声明。

# 7. 异常处理与返回值

## 7.1 服务层

- 业务错误抛 `AppError`；数据库/网络错误转换为内部错误码，不泄露原始信息。
- 不把异常当正常流程；不用异常控制分支。
- 事务失败必须回滚；部分成功必须显式处理或整体失败。
- 只捕获能处理的异常；不能处理的向上抛。

## 7.2 边界层

- Route Handler / Server Action 统一捕获，映射为问题详情或表单错误。
- 记录错误日志：错误码、请求 ID、路由、方法、耗时、上下文；不记录正文与个人信息。
- 未分类异常返回 `K1-SYS-000` + 500；生产环境不返回堆栈。
- 404/409/422 等业务错误按错误码表映射，不得统一返回 500。

## 7.3 前端

- 使用错误边界捕获渲染异常；不得让白屏静默。
- 表单错误显示在字段旁或统一提示区；错误语义使用红色文字直陈，不加底色方框、不加图标。
- 网络失败提供重试入口；重复提交由按钮禁用状态与幂等键共同防止。
- 禁止在客户端捕获异常后吞掉；必须上报且给用户可理解的反馈。

# 8. 可观测性

- 结构化日志：`timestamp`、`level`、`requestId`、`route`、`method`、`status`、`durationMs`、`errorCode`。
- 不记录：评论正文、邮箱、IP、Cookie、Authorization、完整 UA。
- 错误日志可记录堆栈，但只在服务端；日志文件权限最小化。
- 健康检查：`live` 只检查进程；`ready` 检查数据库可读与迁移版本。
- 指标：请求量、错误率、P95、评论写入失败率、数据库大小、备份状态、磁盘剩余。
- 日志滚动与保留：应用日志 14 天；Nginx 访问日志 30 天；审计日志 180 天；备份 30 天。
- 告警：服务不可用、5xx 比例突增、评论写入连续失败、磁盘不足、备份失败。

# 9. 依赖与版本治理

- 包管理器固定 `pnpm`；提交 `pnpm-lock.yaml`；CI 使用 `--frozen-lockfile`。
- 依赖版本锁定，禁止 `latest` / 范围过宽；升级单独 PR，附变更原因与验证。
- 运行时依赖与开发依赖分离；生产镜像不安装开发依赖。
- 新增依赖前检查：许可证、维护活跃度、安全记录、体积、是否可用标准库替代。
- 禁止为一个小组件引入整套 UI 库；禁止为一次性逻辑引入通用工具包。
- 禁止引入与设计系统冲突的默认主题库。
- 依赖升级后必须重新跑构建、测试、视觉与性能门禁。
