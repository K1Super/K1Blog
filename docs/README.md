> 适用对象：K1Blog 的设计、开发、内容、评审、测试、部署与运维

## 0. 这份文档解决什么问题

K1Blog 不是模板化博客，也不是一次性演示页。它要求长期可维护、可追溯、可安全接手，并在视觉、交互、内容与工程四个层面保持同一套标准。

`docs/` 下的文档不是说明材料，而是执行标准。任何设计、编码、内容发布、评审、测试、部署行为，都以这里写下的条款为准。没有写在文档里的做法，不得以「惯例」「先这样」「以后再说」直接进入主线。

## 2. 效力与冲突裁决

### 2.1 优先级

1. 安全合规与人格刚性底线
2. 用户明确的需求与体验取舍
3. 功能正确性
4. 可读性与可维护性
5. 性能优化

人格条款的优先级为：刚性底线 > 验证门禁 > 反模式红牌 > 执行协议 > 表达偏好。

### 2.2 文档之间的冲突

- `00` 高于 `01`–`06`；其余文档同等效力。
- 同一事项在不同文档出现冲突时，取更严格、更可验证的一方，并在一周内修正被弱化的一方。
- 代码行为与文档冲突时，代码是当前事实，但文档是目标标准；不得以「代码已经这样」为由放弃修正。必须在同一变更内更新文档或代码，二者不能长期分叉。
- 涉及框架版本敏感行为（Next.js 的 `proxy.ts` / `middleware.ts`、Route Handler 缓存语义、React 版本行为等）时，以当前锁定版本的官方文档与实测行为为准；不得把训练记忆当作项目事实。
- 任何降级必须按 `00` 第 7 节声明，不得静默降低标准。

### 2.3 与视觉基准的关系

生产实现是唯一的视觉基准（`app/`、`components/`、`styles/`）。历史上用于选型的独立视觉样张已移除，不再作为评审依据：

- 生产实现按 `04` 的 token 与组件规范维护，不得恢复已废弃的品牌叙事。
- 字体采用「展示字体子集 + 系统中文黑体正文」策略，详见 `docs/adr/ADR-0002-font-performance.md`。
- 示例内容为原创演示数据，不得作为真实内容上线。

## 3. 项目基线

| 项 | 基线 |
| --- | --- |
| 站点定位 | 单人维护、夜间阅读、长文优先的原创博客 |
| 视觉主线 | 低照度、编号、刻度、精密的写作界面；深色/浅色双主题 |
| 框架 | Next.js App Router，React 19，TypeScript strict |
| 样式 | Tailwind CSS v4 + 自建设计 token，不使用 shadcn 默认主题 |
| 内容 | 仓库内 MDX，Git 即版本库，无外部 CMS |
| 搜索 | 构建期 Orama 索引 + 客户端搜索，中文分词使用 Mandarin tokenizer |
| 评论 | 原生评论子系统，SQLite + Drizzle，UI 完全自建 |
| 管理端 | Better Auth 保护的管理员会话，留言自动化、策略参数与审计 |
| 数据 | SQLite（WAL），单实例自托管；备份可恢复 |
| 边缘 | Nginx：TLS、HTTP/2、安全响应头、限流、缓存、反向代理 |
| 部署 | Docker 多阶段构建，Next standalone，非 root 运行，Node 22 LTS |
| 质量 | ESLint + Prettier + Vitest + Playwright + Lighthouse CI + 安全扫描 |
| 内容语言 | 中文为主，保留必要的英文技术元数据 |
| 运行环境 | Node 22 LTS（>= 22.0.0）；本地与生产统一 |

以上是工程初始化时的基线。版本号在脚手架落地时锁定到 `package.json` 与 `pnpm-lock.yaml`；任何偏离必须按 `02` 的依赖准入流程记录。

## 4. 使用方式

### 4.1 每次任务开始前

1. 读 `00` 的启动序列与相关条款。
2. 按任务类型读取对应文档：入口 → `01`；接口/数据/安全 → `02`；架构/前端/测试 → `03`；UI → `04`；内容/评论 → `05`；合并/发布 → `06`。
3. 在改动说明中标注适用的文档编号与条款。
4. 只读到能支撑判断为止，未读部分在结论中标注范围。

### 4.2 每次合并前

- 对照 `06` 的门禁清单逐项给出证据。
- UI 改动附 390 / 768 / 1440 / 1920 四档截图、深色/浅色双主题、减弱动效状态。
- 数据改动附迁移脚本、备份路径、恢复验证。
- 评论/认证/安全改动附攻击面检查与失败路径测试。
- 文档改动本身也要走同一套评审，不允许「只改文档就不验证」。

## 5. 完成定义（DoD）摘要

一项工作只有同时满足以下条件，才可称为「完成」：

1. 目标与验收判据已被明确写出，且实际达成。
2. 改动范围最小，没有夹带无关变更。
3. 构建、类型检查、Lint、单元/集成测试通过；有 UI 时完成视觉与无障碍验收；有接口时完成契约与失败路径测试；有数据时完成迁移与恢复验证。
4. 安全、性能、可维护、接手四个视角已按相关性自审。
5. 证据可复现：命令、输出、截图、指标或操作步骤可被他人重复。
6. 未验证项、已知限制、风险与待决项已明确标注，没有把推断写成事实。
7. 相关文档已同步更新，没有留下与实现冲突的旧条款。

详细门禁见 `06`。

## 6. 文档变更

- 文档与代码同仓、同评审、同版本。
- 文档版本采用 `MAJOR.MINOR.PATCH`：破坏性规则变更升 MAJOR，新增约束升 MINOR，措辞与示例修正升 PATCH。
- 每次变更在文末「变更记录」中写明日期、版本、变更点与原因。
- 新增文档必须先更新本总览的文档地图，否则视为未生效。
- 删除或弱化条款必须说明替代方案与风险评估，不得静默删除。
