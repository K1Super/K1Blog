# K1Blog 入口文件与装配规范

> 文档编号：01  
> 版本：v1.0.0  
> 上游：`00-项目执行宪法`  
> 适用范围：Next.js App Router 入口、Route Handler、Server Action、Nginx 边缘入口、Docker 启动链路

## 0. 目的

把「入口文件只做装配、调度、安全前置与生命周期管理」落成 K1Blog 的可执行规范。任何业务逻辑、数据处理、SQL、页面交互实现，都必须下沉到 `features/`、`lib/`、`components/`。

## 1. 核心定位与红线

入口文件的唯一职责：

1. 应用容器装配；
2. 依赖加载与初始化调度；
3. 生命周期管理；
4. 安全前置校验；
5. 错误边界与可观测性挂载。

不可突破的红线：

- 入口零业务：不写业务判断、循环计算、数据增删改查、状态机、页面交互实现。
- 入口零硬编码：地址、端口、密钥、开关、站点 URL 一律来自经校验的环境变量或配置。
- 入口零静默失败：启动阶段缺少必需配置、数据库不可用、迁移失败，直接终止并输出可定位日志，拒绝带病运行。
- 入口零秘密：不打印、不返回、不写入密钥、令牌、邮箱、IP 明文。

## 3. 固定装配流水线

### 3.1 构建期

1. 读取并校验构建环境变量。
2. 校验 MDX frontmatter schema、slug 唯一性、标签合法性、草稿状态。
3. 生成静态文章、标签、归档页面。
4. 生成搜索索引、RSS、sitemap、OG 资源。
5. 任何 schema 错误、重复 slug、缺失必填字段，直接使构建失败。

### 3.2 容器启动期

1. Nginx 启动或等待上游健康。
2. `scripts/entrypoint.mjs` 校验运行时环境变量。
3. 打开 SQLite：`journal_mode=WAL`、`busy_timeout`、`foreign_keys=ON`。
4. 执行未应用的迁移；失败即终止。
5. 启动 Next standalone 服务，监听 `HOSTNAME` / `PORT`。
6. 健康检查通过后，Nginx 开始转发。
7. 注册 `SIGTERM` / `SIGINT` 优雅停机。

### 3.3 请求期

```text
Nginx（TLS / 安全头 / 请求 ID / 限流 / 请求体限制）
  → Next 边缘（proxy/middleware，仅轻量安全判断）
  → 路由（page / route handler / server action）
  → feature service（业务规则）
  → lib/db（SQLite / Drizzle）
```

禁止在 `route.ts` 中直接调用 `lib/db`；禁止在 `proxy.ts` 中访问数据库。

### 3.4 停机期

1. 收到 `SIGTERM` / `SIGINT` 后停止接受新请求。
2. 等待进行中的请求完成，最长等待 20 秒。
3. 执行 SQLite WAL checkpoint（`wal_checkpoint(TRUNCATE)`，无写入时）。
4. 关闭数据库连接、日志刷新、退出进程。
5. Nginx 侧配置 `proxy_read_timeout` 与健康检查，避免请求悬挂。
6. 若超时仍未退出，由容器运行时强制终止；停机过程必须产生日志。

## 4. 各入口职责细则

### 4.1 `app/layout.tsx`

必须：

- 只负责根文档结构、字体加载、主题初始化、全局 Provider、基础 metadata。
- 主题恢复脚本必须最小化，避免阻塞首屏；不得读取数据库或 cookies 做业务判断。
- 只允许必要的基础客户端组件；不得把重交互组件挂到根布局。
- 字体只加载首屏需要的子集；其余按需。

禁止：

- 数据请求、SQL、Markdown 解析；
- 在根布局里写导航业务、权限判断、评论逻辑；
- 引入大型图表、编辑器、3D 库。

### 4.2 `app/page.tsx`、文章页与标签页

必须：

- 只调用 `features/content` 的查询函数，组合页面区块。
- `generateStaticParams` 只导出静态参数，不写业务。
- metadata 只做映射，不拼复杂业务逻辑。
- 文章页的正文渲染交给 `features/content` 的 MDX 渲染器。

禁止：

- 在页面文件里 `fs.readFile`、`gray-matter` 解析、MDX 编译、SQL 查询；
- 在页面文件里实现评论提交、搜索算法、分页业务。

### 4.3 Route Handler

统一顺序：

1. 生成或读取请求 ID；
2. 解析路径参数与查询参数；
3. Zod 校验；
4. 会话/权限校验（仅管理端）；
5. 限流与幂等校验（仅写接口）；
6. 调用 feature service；
7. 统一响应/错误映射；
8. 记录结构化日志（不含敏感信息）。

Route Handler 不得：

- 写 SQL、拼 SQL、直接操作 Drizzle；
- 实现业务规则；
- 返回 `err.stack`、SQL 错误、内部路径；
- 用 `any` 绕过入参类型；
- 在 GET 中产生副作用。

### 4.4 Server Action

- 仅用于同源表单与受控交互；对外 API 仍走 `/api/v1`。
- 必须做 Zod 校验、会话/权限校验、限流/幂等、错误映射。
- 成功后按需 `revalidatePath` / `revalidateTag`；不得无差别刷新全站。
- 不得把内部异常或数据库错误直接返回给客户端。

### 4.5 `instrumentation.ts`

- 只做环境校验、日志/监控注册、错误上报钩子。
- 不得写业务、不得写数据库、不得启动长时间后台任务。
- 启动校验失败必须抛出并终止进程；日志必须脱敏。

### 4.6 `proxy.ts` / `middleware.ts`

- 只做请求 ID、安全响应头、规范化重定向、粗粒度限流前置。
- 不得访问数据库、文件系统、Node 专有 API。
- 不得做会话查询、用户资料查询、评论查询。
- 限流真正生效点仍在应用服务层与 Nginx；边缘层只做前置拦截。

### 4.7 `next.config.ts`

- 只做静态配置：安全头、图片域名与格式、字体、重定向、MDX 集成、构建输出。
- 不得读取秘密、不得连接数据库、不得写业务分支。
- 安全头必须与 `deploy/nginx.conf` 一致；重复设置时以更严格者为准。

### 4.8 `scripts/entrypoint.mjs`

- 纯 ASCII 输出，避免 Windows 终端编码与启动脚本异常。
- 校验环境变量后执行迁移；迁移失败直接退出非零码。
- 启动 standalone 服务并处理信号。
- 不把数据库连接、密钥打印到 stdout。
- 版本号只从 `package.json` 读取，不在脚本内重复维护。

### 4.9 `deploy/nginx.conf`

必须覆盖：

- TLS 1.2/1.3、HTTP/2、HSTS；
- `server_tokens off`；
- 安全响应头：CSP、`X-Content-Type-Options`、`Referrer-Policy`、`Permissions-Policy`、`X-Frame-Options` / `frame-ancestors`；
- 请求体大小限制（评论接口单独收紧）；
- `limit_req` 对登录、评论写接口限流；
- 静态资源 immutable 缓存；
- `proxy_http_version 1.1`、`Connection ""`、合理的 `proxy_read_timeout`；
- 请求 ID 注入与日志；
- 健康检查路径不缓存；
- 禁止把内部错误页、堆栈暴露给客户端。

## 5. 启动快速失败

必需运行时配置至少包括：

```text
APP_ENV
SITE_URL
DATABASE_PATH
BETTER_AUTH_SECRET
COMMENT_IP_PEPPER
SMTP_URL（启用邮件通知时必需）
```

`BETTER_AUTH_URL` 默认取 `SITE_URL`；如显式设置，必须与站点规范域名一致。

管理员初始化不通过生产环境变量：使用一次性本地 CLI 创建首个管理员，完成后移除凭据；禁止把 bootstrap 密码/哈希长期存放在生产配置中。

规则：

- 缺失、为空、格式非法、生产环境使用示例值：启动失败。
- 数据库无法打开、迁移失败、`PRAGMA quick_check` 失败：启动失败。
- 生产环境不得开启调试模式、详细错误、测试端点。
- 启动日志只输出环境名、版本、监听地址、迁移版本；不输出密钥与完整连接串。

## 6. 环境隔离

- 本地：`.env.local`，不提交；`.env.example` 只放键名与说明，不放真实值。
- 预发/生产：容器环境变量或密钥托管；Nginx 侧不落明文密钥。
- `NEXT_PUBLIC_` 只允许非秘密、可公开的配置；任何密钥、令牌、邮箱、IP 禁止进入。
- 入口不硬编码站点 URL、端口、CDN 地址、SMTP 地址。
- 构建期与运行期环境变量分离；不得把构建机秘密带入镜像。

## 7. 可观测性

- 每个请求有 `X-Request-Id`，贯穿 Nginx 日志、应用日志、错误上报。
- 日志为结构化 JSON：时间、级别、请求 ID、路由、方法、状态码、耗时、错误码；不记录正文、邮箱、IP 明文、令牌。
- 启动记录：版本、环境、迁移版本、启动耗时。
- 健康检查：`/api/v1/health/live`（进程存活）与 `/api/v1/health/ready`（数据库可读）。
- 错误响应只返回错误码、友好消息、请求 ID；堆栈只进服务端日志。
- 监控指标至少覆盖：请求量、错误率、P95 延迟、评论写入失败率、数据库大小、备份状态。

## 8. 体积与轻量化

| 项 | 约束 |
| --- | --- |
| 根布局客户端组件 | 只允许主题切换等小型交互，禁止重库 |
| 首页首屏 JS | 目标 ≤ 160KB gzip；门禁 ≤ 180KB gzip |
| Route Handler | 不引入 UI、图表、编辑器依赖 |
| 字体 | 首屏只加载必要子集；preload ≤ 2 个文件 |
| 图片 | `next/image`（`unoptimized`）+ 预生成 AVIF/WebP；单图 ≤ 200KB |
| 第三方库 | 新引入必须按 `02` 依赖准入；能用标准库不引 |

规则：

- Next 约定文件使用框架要求的固定命名；
- 其余源码文件使用 kebab-case；
- React 组件文件使用 PascalCase 文件名，组件导出名与文件名一致；
- 测试文件与源文件同目录或 `tests/` 分层，命名 `*.test.ts(x)` / `*.spec.ts(x)`；
- 禁止在 `app/` 下堆放业务工具、类型、常量；这些放到 `features/` 或 `lib/`。

## 10. 禁止黑名单（CR 直接驳回）

1. 入口文件写业务逻辑、SQL、复杂状态机。
2. 硬编码 IP、端口、域名、站点 URL、密钥、账号、SMTP 凭据。
3. 在 `proxy.ts` / `middleware.ts` 中访问数据库、Node API、文件系统。
4. 在 Route Handler 中直接访问 Drizzle/SQLite，绕过 feature service。
5. 未校验入参就写库或返回数据。
6. 错误响应暴露堆栈、SQL、内部路径、密钥。
7. `console.log` 代替结构化日志；日志打印邮箱、IP、令牌明文。
8. 根布局引入大型依赖或重交互组件。
9. `NEXT_PUBLIC_` 中出现秘密。
10. 用 `any` 绕过入口边界类型；用 `@ts-ignore` 掩盖错误。
11. 空 `catch`、默认值吞错、失败静默。
12. 评论写接口缺少限流、幂等、长度校验中的任一项。
13. 管理端写接口缺少会话校验、CSRF 防护、审计日志。
14. 构建/启动脚本包含非 ASCII 字符或硬编码版本号。
15. 在入口直接实例化业务对象、调用业务方法。

## 11. 治理卡点

### 11.1 静态约束

- `lib/db`、`lib/auth`、`lib/env`、日志模块使用 `server-only`，禁止进入客户端 bundle。
- ESLint `import/no-restricted-paths` 或等价边界规则：
  - `app/api/**` 不得直接 import `lib/db`；
  - `components/**` 不得 import `lib/db`、`lib/auth`、`features/**/service`；
  - `lib/**` 不得 import `app/**`、`features/**`；
  - 禁止跨 feature 直接引用内部文件；只允许通过 feature 公开入口。
- 文件行数检查：入口文件超过第 2 节上限，CI 直接失败。
- Route Handler 必须通过统一的 `readJson` / `parseParams` / `errorResponse` 工具；禁止自行拼装响应。
- 禁止在 `app/` 下直接使用 `fs`、`path`、`process.env`；统一走 `lib/env` 与 feature 查询。

### 11.2 测试卡点

- 每个 Route Handler 至少覆盖：成功、参数非法、未认证/无权限（如适用）、限流/幂等（如适用）、服务异常映射。
- 每个 Server Action 至少覆盖：成功、校验失败、权限失败、异常映射。
- 启动脚本至少覆盖：环境缺失失败、迁移失败失败、正常启动、信号停机。
- Nginx 配置必须 `nginx -t` 通过；安全头与限流规则有配置测试或人工核对记录。

### 11.3 评审卡点

入口相关 PR 必须附：

- 入口职责说明；
- 变更前后的请求链路；
- 失败路径与回滚方式；
- 构建、类型检查、测试、Lint、健康检查证据；
- 涉及 UI 时附 `04` 要求的截图矩阵。

## 12. 入口审查清单

- [ ] 入口文件是否只做装配/调度/安全/生命周期？
- [ ] 是否出现业务判断、SQL、复杂状态机？
- [ ] 是否直接读取 `process.env` 而绕过 `lib/env`？
- [ ] 是否有硬编码地址、端口、密钥、站点 URL？
- [ ] 错误响应是否可能泄露内部信息？
- [ ] 日志是否可能泄露邮箱、IP、令牌？
- [ ] 评论/管理端入口是否具备限流、幂等、CSRF、审计？
- [ ] 是否引入了不必要的重型依赖？
- [ ] 启动失败是否快速失败，而不是带病运行？
- [ ] 停机是否释放数据库与日志资源？
- [ ] 文件是否超过行数上限？
- [ ] 是否有对应的成功/失败路径测试？
- [ ] Nginx 安全头、限流、缓存、请求体限制是否一致？

## 13. 版本敏感说明

- Next.js 16 的 `proxy.ts` 与旧版本 `middleware.ts` 的行为、匹配范围不同，必须以锁定版本官方文档为准。
